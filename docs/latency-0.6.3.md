# FlowType 0.6.3 延迟排查

## 用户遇到的现象

输入框出字变慢，松手后转圈较久，转圈期间再次按快捷键没有反应。此次修复没有增加独立文字弹框，也没有改为后台常开麦克风。

## 原因与修改

1. **音频被重复限速。** AudioWorklet 已按音频时钟生成 20ms PCM 帧，主进程又给每一帧添加 20ms 的定时等待。Windows 定时器并不保证准时唤醒；当每次实际等待约 32ms 时，上传速度低于采集速度，积压随说话时长增加。连接建立前积累的音频也不能及时追上。
2. **收尾锁住下一轮录音。** `startRecording` 在上一轮 `finishing` 时直接返回。即使麦克风已经停止，仍要等云端结束事件才能再次录音。
3. **原验证未反映真实采集节奏。** 旧接口测试用 100ms 音频块，随后尝试的固定 20ms 计时器也会把测试语音本身拉长。这两种方式都容易掩盖发送队列的问题。新的合成语音测试按经过的真实时间补齐 20ms 帧，模拟工作线程的音频时钟。

正常录音现在立即发送已采集的数据，并有界合并积压；大批积压分批让出事件循环，不增加逐帧等待。重试保留原来的回放节奏和一次重试限制。

采集与云端收尾按会话 ID 分离。上一轮的尾帧、停止确认、错误和最终文字仍路由回原会话；不会释放新一轮麦克风、覆盖新一轮波形或丢弃上一轮历史。输出队列只让后续文字等待前一轮完成，不阻塞麦克风。取消、失败和超时都释放输出顺序等待；手动编辑、焦点变化和锁屏使旧自动回填失效。

## 测量结果

同一次排查中使用相同约 10.11 秒的内存合成语音，调用真实千问 API。没有使用用户麦克风、鼠标、键盘或输入框。

| 指标 | 0.6.2 | 0.6.3 |
| --- | ---: | ---: |
| 实际送入采集帧的时长 | 10,153ms | 10,140ms |
| 首次草稿返回 | 977ms | 590ms |
| 首次确认文字返回 | 6,701ms | 4,352ms |
| 松手到云端收尾完成 | 5,852ms | 67ms |

这是一组合成音频对照，不是所有网络、设备或真实说话场景的延迟承诺。软件不再人为积压音频，但仍需等待模型确认结果，不会冒险把可变草稿插入后再删除用户输入。确认前缀和可修订草稿的区别参见[千问官方服务端事件](https://help.aliyun.com/zh/model-studio/qwen-asr-realtime-server-events)。

可重复的内部压力测试模拟 60 秒音频和 32ms 定时器唤醒：旧实现积压 22,780ms，新实现积压 0ms，且采样字节数完全一致。该数字衡量本地发送队列，不是网络传输耗时。

## 回归与诊断

- `npm test`：发送吞吐、连接追赶、多轮重叠、顺序输入、迟到尾帧、取消、断网、采集停止超时、手动编辑和历史保留。
- `npm run verify:realtime`：按真实音频时钟送入 20ms 合成语音帧，验证确认增量与最终文字完全一致，并输出延迟指标。
- `node scripts/run-electron-check.mjs verify-live-api.cjs --speech --flow --baseline`：从已提交的 0.6.2 版本加载旧发送实现，使用相同测试输入作对照。
- 运行日志新增首次确认文字、释放时剩余上传音频、收尾时长、输入辅助进程耗时和连接关闭码。日志不记录 Key、音频或识别正文。

剪贴板的条件恢复机制保持不变；没有用缩短粘贴保护等待来换取容易丢字的假性提速。实际微信、浏览器和其他输入框体验由用户手动验收。
